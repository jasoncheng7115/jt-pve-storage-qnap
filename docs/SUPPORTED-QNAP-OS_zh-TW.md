# 這個 plugin 支援的 QNAP 作業系統

簡要來說，**它是針對 QTS 5.1 與 QuTS hero h5.1 撰寫的**。比 QTS 4.5.1 更舊的版本，會在新增 storage 時直接被拒絕，不會等到之後才發現。**QuTS hero h6.0 以上尚未支援**，同樣會在新增時被拒絕。

這一頁把「支援」、「應可運作」與「不支援」分開說明，因為前後兩個是確定的答案，中間那個不是。

---

## 一、必要條件：Storage Manager V2

QNAP 有兩代 Storage Manager，兩者是**兩套不同的 CGI 呼叫**，不是同一套 API 的兩個版本。這個 plugin 只實作 V2。

韌體會回報自己是哪一種。`authLogin.cgi` 會回傳：

| `<storage_v2>` | `<is_zfs>` | 代表的意義 | 這個 plugin |
|---|---|---|---|
| 不存在，或 `0` | 任何值 | 舊版 Storage Manager | **拒絕** |
| `1` | `0` | LVM 上的 Storage Manager V2（QTS）| 支援 |
| `1` | `1` | ZFS（QuTS hero）| h5.x 支援，並且可以使用即時複製。h6.0 以上**拒絕** |

`pvesm add` 在寫入任何東西之前就會做這項檢查。太舊的韌體會立刻失敗，訊息裡會寫出版本，不會先新增成功，之後才列不出任何東西。

QuTS hero h6.0 以上同樣回報 Storage Manager V2，但這個 plugin 仍然無法在上面運作。這一項是依韌體版本判斷的，也在同一個時間點拒絕。見第三節。

安裝之前可以先確認：

```
pve-qnap-api-probe --host <nas> --user admin --insecure
```

## 二、支援對照表

| 作業系統 | 版本 | 狀態 | 說明 |
|---|---|---|---|
| **QTS** | **5.1.x** | **支援** | 這個 plugin 撰寫時所針對的韌體版本 |
| QTS | 5.2.x | 應可運作 | 同一套 API，尚未驗證。歡迎回報實際狀況 |
| QTS | 4.5.1 至 5.0.x | 應可運作 | `storage_v2` 從這個版本開始出現，尚未驗證 |
| QTS | 4.5.0 以下 | **不支援** | 舊版 Storage Manager，`pvesm add` 會直接拒絕 |
| **QuTS hero** | **h5.1.x** | **支援** | ZFS。可以使用即時複製，所以 Proxmox VE 的連結複製會立即完成 |
| QuTS hero | h5.2.x | 應可運作 | 尚未驗證 |
| QuTS hero | h4.5.x 至 h5.0.x | 應可運作 | 尚未驗證 |
| QuTS hero | h6.0 以上 | **尚未支援** | 已在 h6.0.1 上量測過。`pvesm add` 會直接拒絕。見第三節 |
| QuTScloud | 任何版本 | **不支援** | 雲端映像檔，沒有這種形式的本機儲存集區 |
| QNE Network OS | 任何版本 | **不支援** | 不同的產品，沒有 Storage Manager |
| TR 系列擴充櫃上的 QTS | 任何版本 | 不適用 | 擴充櫃不是 NAS |

「應可運作」的意思是：這個 plugin 用到的部分沒有已知的差異。這不代表有人實際執行過，請當成任何未經測試的組合來看待。

## 三、QuTS hero h6.0 以上：尚未支援

對照表裡只有這一項是實際量測的結果，其他都是依文件判斷。這個 plugin 在一台 QuTS hero h6.0.1 的 NAS 上執行過：

| | 在 h6.0.1 上的結果 |
|---|---|
| 登入，並讀取機型、韌體版本與兩個判別欄位 | 正常 |
| `pve-qnap-api-probe`：portal、儲存集區、LUN、target | 正常 |
| 建立 storage 的 iSCSI target | **被 NAS 拒絕** |
| 建立 LUN | **被 NAS 拒絕** |

所以在 h6 上，storage 的資訊讀得出來，但放不了任何磁碟。從 0.6.1 開始，新增 storage 時 plugin 會直接拒絕 QuTS hero h6.0 以上的韌體，不會先送出 NAS 會拒絕的呼叫，訊息裡會寫出韌體版本。

**已經放有這個 plugin 磁碟的 NAS，請不要升級到 QuTS hero h6**。升級之後，storage 仍然會回報容量、列出磁碟，但無法建立或刪除任何磁碟。這時 plugin 的錯誤訊息會寫出韌體版本。升級過程中，執行中的 guest 是否還能繼續使用原本的磁碟，尚未量測。

## 四、QTS 與 QuTS hero 的差別：連結複製只在 QuTS hero 提供

兩者都支援。差別只在一個操作，但影響很大。

這個 plugin 的每一次複製，都是在 NAS 上從快照建立的。在 **QuTS hero** 上是即時複製，新的 LUN 與快照共用區塊，所以連結複製會立即完成，而且不佔用額外空間。在 **QTS** 上，複製會把整顆磁碟複製一份，而 Proxmox VE 會中止超過 60 秒的儲存端複製。所以 plugin 在 QTS 上不提供：連結複製與從快照複製，Proxmox VE 會在開始之前就拒絕。

| | QTS（LVM）| QuTS hero（ZFS）|
|---|---|---|
| 快照 | 支援 | 支援 |
| 倒回 | 支援。需要的時間取決於 NAS 把磁碟寫回去要多久 | 支援 |
| 連結複製、從快照複製 | **不提供** | 即時 |
| 範本 | 支援，以完整複製的方式複製 | 支援 |
| 完整複製 | 由 Proxmox VE 複製資料 | 由 Proxmox VE 複製資料 |
| 大量從範本部署 | 慢 | 快 |

如果正在為 Proxmox VE 叢集選購硬體，而且預期會大量從範本部署，這一點是決定性的因素。

**在 QTS 上，範本請使用完整複製**：`qm clone <vmid> <newid> --full 1`，或在網頁介面選擇「完整複製」。這是由 Proxmox VE 自己複製資料，不受上述時間限制。

plugin 在同一台 NAS 上一次只執行一個倒回或複製。這段期間從任何節點啟動的第二個，都會被拒絕，訊息會說明正在執行的是什麼、在哪個節點、從什麼時候開始。

在 QuTS hero 上還有一件事需要知道：即時複製會以來源快照作為自己的基礎。所以 plugin 會在範本上保留一個快照。還有連結複製存在時，刪除範本會失敗，訊息裡會引用 NAS 的回應。

## 五、機型需求與韌體版本是兩回事

機型可以執行支援的韌體，卻仍然不符合需求。

* **iSCSI target 服務**：範圍內的每一台 NAS 都有，但出廠時是**停用**的。請到「儲存與快照總管 → iSCSI 與光纖通道」啟用。服務停用時，plugin 會拒絕新增 storage，並說明原因。
* **儲存集區**：這個 plugin 建立的是區塊型 LUN，必須放在儲存集區裡。磁碟設定成靜態磁碟區的 NAS，沒有可用的儲存集區。
* **快照**：QNAP 的入門機型完全不支援 iSCSI LUN 快照，而且 **plugin 無法事先檢查**。新增 storage 時 plugin 會提出警告，請先對一顆測試磁碟建立一次快照，再開始使用這個功能。請查閱機型規格頁上的「快照」欄位。
* **足夠的 LUN 數量**：一顆虛擬機磁碟就是一個 LUN。QNAP 公布的數字是 QTS 128、QuTS hero 256，plugin 會向 NAS 讀取上限，不自行假設，`pve-qnap-api-probe` 會印出來。這是這個 storage 實際的上限，剩餘空間再多也無法改變。見 [LIMITS_zh-TW.md](LIMITS_zh-TW.md)。

## 六、Proxmox VE

| | 版本 |
|---|---|
| Proxmox VE | 9.x。storage API 版本可以協商到 10，所以 8.x 預期可以運作，但從未測試過 |
| Storage plugin API | 10 至 15，載入時協商 |

API 版本是協商出來的，不是固定寫在程式裡。如果宣稱的版本高於節點自己的版本，PVE 會直接拒絕整個 plugin，該節點上所有這個類型的 storage 都會消失。

套件必須安裝在**叢集中的每一個節點**上。

## 七、組合不在表上時

請執行探索工具，並把輸出提供給我們。它會印出機型、韌體、兩個判別欄位、數量上限與儲存集區，而且不會建立任何東西：

```
pve-qnap-api-probe --host <nas> --user admin --insecure --node
```
